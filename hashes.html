Hash / MAC / KDF / FIELD GUIDE

A digest is not
an authenticator

Hash functions, keyed authentication, key derivation and password storage have separate contracts.

Three resistance propertiesHMAC adds a shared authentication secretHKDF extracts and expands keying materialPassword storage deliberately spends time and memory
01 / FIELD NOTES

Three resistance properties

The work factors below are generic classical estimates for an ideal n-bit digest.

PropertyAttacker taskGeneric cost
PreimageGiven y, find x with H(x)=y≈ 2^n
Second preimageGiven x, find another x′ with the same hash≈ 2^n
CollisionChoose any distinct x,x′ with equal hashes≈ 2^(n/2)

SHA-256 / SHA-512 are SHA-2 choices; SHA-3 uses a different sponge design, and SHAKE is an extendable-output function. A hash is deterministic and usually public. An attacker able to replace both a file and its published hash can preserve a successful comparison. MD5 and SHA-1 are historical examples of broken collision resistance, not choices for new signature-integrity designs.

Read the source: FIPS 180-4: SHA-2 ↗ · FIPS 202: SHA-3 / SHAKE ↗ · Boneh–Shoup: A Graduate Course in Applied Cryptography ↗

02 / FIELD NOTES

HMAC adds a shared authentication secret

A plain hash cannot identify who created a message.

tag = HMAC(key, encoded_message) accept only if constant_time_compare(expected_tag, received_tag)

HMAC uses a specific nested keyed-hash construction. Do not replace it with H(secret || message): Merkle–Damgård hashes can allow length extension in that construction. Every holder of the MAC key can create a valid tag, so HMAC does not offer public verification or distinguish those holders. Use different keys and domain labels across protocols.

Read the source: RFC 2104: HMAC ↗

03 / FIELD NOTES

HKDF extracts and expands keying material

A KDF organizes entropy; it does not create entropy from an easy password.

PRK = HKDF-Extract(salt, input_key_material) K_enc = HKDF-Expand(PRK, "protocol-v1/encryption", length) K_auth = HKDF-Expand(PRK, "protocol-v1/authentication", length)

Salt and context/info have different roles. Salt need not be secret; info separates purposes and binds context. Use the protocol’s exact labels and sizes. Key establishment outputs should normally pass through the specified KDF before becoming AEAD keys.

Read the source: RFC 5869: HKDF ↗

04 / FIELD NOTES

Password storage deliberately spends time and memory

A random salt prevents reusable cross-user precomputation, not single-user guessing.

Use a password-hashing design such as Argon2id with calibrated memory/time parameters and a unique salt. Store the algorithm version and parameters for future upgrades. Fast SHA-256, even with a salt, gives offline attackers a cheap guess loop. HKDF is not a password-hardening function. A pepper is an additional managed secret and introduces a separate recovery and rotation problem.

Read the source: RFC 9106: Argon2 ↗ · RFC 5869: HKDF ↗
