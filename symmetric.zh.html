用共享密钥
保护大量数据

理解分组与流密码、认证模式、Nonce 规则，以及足以破坏好算法的使用错误。

01 / FIELD NOTES

AES 与流密码的接口不同

AES 是单个分组上的带密钥置换；模式把它组成消息构造。

构造机制记住什么
AES-128 / 192 / 256128 位分组；10 / 12 / 14 轮密钥长度改变轮数，不改变分组长度
CTR / ChaCha20产生密钥流，再与明文 XOR重复 key/nonce 可能重复密钥流
ECB逐分组独立加密相同输入分组泄露模式，不适合普通消息加密
CBC使用 IV 和填充链接分组需要不可预测 IV 和另行认证；存在填充 Oracle 风险

对应资料：FIPS 197：AES ↗ · RFC 8439：ChaCha20-Poly1305 ↗ · Boneh–Shoup：应用密码学教材 ↗

02 / FIELD NOTES

AEAD 认证密文和可见上下文

遵守模式定义的 Nonce 和 Tag 要求。

(ciphertext, tag) = Seal(key, nonce, plaintext, associated_data) plaintext or FAIL = Open(key, nonce, ciphertext, tag, associated_data)

AES-GCM 与 ChaCha20-Poly1305 结合加密和认证。关联数据可见但经过认证，可绑定版本、租户、内容类型或序号。接收方必须提供相同关联数据，并在使用明文前拒绝认证失败。

对应资料：SP 800-38D：GCM ↗ · RFC 8439：ChaCha20-Poly1305 ↗ · Python cryptography：AEAD 接口 ↗

03 / FIELD NOTES

唯一性是生命周期问题

随机 Nonce 不能自动解决重启与并发。

AES-GCM 不应在相同密钥下复用 Nonce。96 位 Nonce 是常见的高效选择，但仍受规范上限约束。ChaCha20-Poly1305 也要求唯一性。计数器分配要处理并发、崩溃和 VM 快照；随机分配要计算碰撞预算。恢复旧 key/nonce 状态时，密钥轮换本身也不能解决问题。

C1 = P1 XOR S C2 = P2 XOR S C1 XOR C2 = P1 XOR P2 # if the same keystream S is reused
真实性不等于防重放

未修改的认证记录可以验证两次。协议序号或请求状态需要另行跟踪。XTS 磁盘加密解决另一类问题，不提供 AEAD 式数据认证。

对应资料：SP 800-38D：GCM ↗ · RFC 8439：ChaCha20-Poly1305 ↗

04 / FIELD NOTES

一个有用的实现练习

既验证正确往返，也验证失败行为。

  • 加密一条记录，分别修改密文、Tag 与 AAD；每个修改后的记录都应认证失败。
  • 写清 Nonce 分配如何在重启和多个写入者之间保持唯一。
  • 按所选算法及协议设置记录大小和密钥使用预算，不设想无限使用寿命。
