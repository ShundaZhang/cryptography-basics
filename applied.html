01 / FIELD NOTES

Envelope encryption separates data and key control

A data-encryption key protects an object; a managed key protects that key.

Generate a DEK with a CSPRNG, encrypt the object with AEAD, and wrap/protect the DEK using a KMS/HSM-managed KEK or a defined recipient scheme. Store nonce, tag, algorithm/version, authenticated metadata and wrapped key together. KEK rotation can rewrap DEKs; a compromised DEK normally requires new data encryption. KMS authorization, tenant binding and audit are still essential.

03 / FIELD NOTES

Correct mathematics still needs a robust implementation

The platform can expose secrets through behavior.

Use maintained high-level library APIs. Avoid data-dependent secret branches, variable-time comparisons, unsafe parsing and exposing decryption distinctions as an oracle. Constant-time source code needs compiler/platform validation; hardware acceleration is not an automatic absence of side channels. Fault handling, key erasure and crash recovery have their own assumptions.

  • Review message formats, algorithms, nonce state and key ownership before reviewing API calls.
  • Test tampering, wrong key, wrong context, stale messages, malformed lengths and rollback behavior.
  • Document library versions, supported profiles and interoperability vectors.

04 / FIELD NOTES

Generation is only the first key-management step

Plan how trust changes over time.

Inventory keys by purpose, owner, algorithm, strength, storage location and cryptoperiod. Plan provisioning, backup/recovery, rotation, revocation, compromise response and destruction. An HSM can restrict key extraction but cannot fix an overly broad signing or decrypt authorization policy. Separate signing, wrapping, encryption and authentication keys.
