01 / FIELD NOTES

Three operations with different security goals

A key pair is not an interchangeable encrypt/sign interface.

OperationPublic inputSecret input / result
Public-key encryptionRecipient encryption keyRecipient private key recovers plaintext
DH / KEM key establishmentDH shares or encapsulation key/ciphertextPrivate inputs produce shared keying material; KDF derives usage keys
Digital signatureVerification key + message + signatureSigning key creates a signature, not a secret message

RSA-OAEP is an encryption scheme; RSA-PSS is a signature scheme. Raw modular exponentiation is neither a safe message cipher nor a complete signature scheme. X25519 is for DH; Ed25519 is for signatures, despite both using related curve mathematics.

02 / FIELD NOTES

Understand agreement with a tiny worked example

The numbers below are deliberately insecure teaching values.

p = 23, g = 5 Alice: a = 6, A = g^a mod p = 8 Bob: b = 15, B = g^b mod p = 19 Alice: B^a mod p = 2 Bob: A^b mod p = 2

Real DH uses vetted groups and validates public inputs as required. Bare DH does not authenticate the peer: an active intermediary can negotiate a different secret with each side. Authenticate the exchange and bind roles and transcript. Ephemeral agreement can provide forward secrecy against later long-term-key compromise, under the protocol’s assumptions.

03 / FIELD NOTES

Signing depends on encoding, nonce handling and identity

ECDSA, EdDSA and RSA-PSS are schemes with specific rules.

ECDSA requires secure per-message scalar generation: reused or biased values can expose the private key. Deterministic generation is one specified approach, not permission to invent a nonce rule. EdDSA uses its own deterministic design; hash/prehash/context variants must match exactly. Sign a specified representation with domain separation; verify with an authenticated key and appropriate algorithm constraints.

A signature is not “private-key encryption”

Verification authenticates the signed bytes under a key. Confidentiality, certificate trust, authorization and replay checks are distinct.

Read the source: RFC 8032: EdDSA ↗ · RFC 8017: PKCS #1 ↗ · Boneh–Shoup: A Graduate Course in Applied Cryptography ↗

04 / FIELD NOTES

A public key needs a trust path

Certificates connect names and keys through a policy-controlled trust chain.

A certificate chain is not accepted merely because every signature is mathematically valid. Check the selected trust anchor, constraints, validity, intended usage, algorithm policy and revocation handling; TLS also checks the intended service name. Pinning and raw keys use different enrollment and rotation models. Losing trust-store control can defeat otherwise correct cryptography.

Read the source: RFC 8446: TLS 1.3 ↗ · SP 800-57 Part 1 Rev. 5: key management ↗
