Labs / FIELD GUIDE

Observe the property
Test the failure

Four local browser experiments using the Web Cryptography API. Inputs and transient keys stay in this page; no experiment data is uploaded or saved. HTTPS or localhost is required.

HashAEADSignaturesNonce reuse
01 / DIGEST

Change one input, compare two digests

Hash is deterministic. A changed digest is not proof of who authored the data.

Ready — choose an experiment

The experiment compares SHA-256 digests and counts changed output bits. Around half is a typical observation, not a promise for every pair or a security proof. The input “hello” also provides a known-answer check.

Read the source: FIPS 180-4: SHA-2 ↗ · W3C Web Cryptography API ↗

02 / AEAD

Decrypt only after authenticating

AES-GCM authenticates the ciphertext and AAD. It does not keep replay history for the application.

Ready — choose an experiment

Each new record uses a newly generated key and random 96-bit nonce in this small exercise. Later actions use that sealed record; editing the input fields takes effect when you create another record. A real system needs per-key nonce limits, persistent uniqueness and protocol replay handling.

Read the source: SP 800-38D: GCM ↗ · W3C Web Cryptography API ↗

03 / SIGNATURE

A signature binds bytes to a key

A mathematical signature check does not establish whether the key belongs to a trusted identity.

Ready — choose an experiment

The browser generates a transient ECDSA P-256 key pair and signs using SHA-256. Only the public key and signature bytes are displayed; the private key is non-extractable and discarded when the page closes. This demo does not create a certificate or assert a person’s identity.

Read the source: W3C Web Cryptography API ↗ · Boneh–Shoup: A Graduate Course in Applied Cryptography ↗

04 / MISUSE

Repeated nonce, repeated keystream

An intentional local misuse experiment with two short synthetic messages.

Ready — choose an experiment

For the overlapping message length, repeated AES-GCM key/nonce exposes C₁ XOR C₂ = P₁ XOR P₂ because the CTR keystream repeats. The last 16 bytes (authentication tag) are excluded from this comparison. This reveals a relationship between plaintexts; it is not a complete GCM forgery demonstration. Never use this setup for real data.

Read the source: SP 800-38D: GCM ↗

05 / NEXT STEPS

Make the checks reproducible

Repeat basic byte, HMAC and key-derivation checks outside the browser.

Download the Python standard-library exercise ↓

python3 core_examples.py

Includes an RFC 5869 HKDF known-answer test, HMAC tamper rejection, random-byte generation and a small Diffie–Hellman arithmetic example. The tiny DH group is for arithmetic only and is insecure for deployment. No hand-written cipher is presented as production code.
